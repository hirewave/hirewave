What is HireWave?
Lab 1–2 · Project

Description

A REST API platform for the freelance market. Clients post projects, freelancers place bids, the client picks the winner.

Tech Stack

  • Java 21 + Spring Boot 3.4
  • MongoDB 6.0 (Spring Data)
  • Jakarta Bean Validation
  • Docker + Docker Compose

Main Flow

OPENproject created
›
IN_PROGRESSbid accepted
›
COMPLETEDdone + rating
OPENproject created
›
CANCELLEDcancelled by client
or directly from OPEN
Bid status: PENDING → ACCEPTED or REJECTED

Accepting a bid automatically bulk-rejects all other PENDING bids on the same project.

Business Rules — BidService
Lab 4 · Service Layer

Submit Bid

  • Project must be OPEN
  • Freelancer must exist
  • No duplicate bid from the same freelancer
  • Freelancer has at least one matching skill
  • Freelancer has fewer than 3 active IN_PROGRESS projects

Accept Bid

  • Accepted bid → ACCEPTED
  • All other PENDING bids → REJECTED (bulk)
  • Project → IN_PROGRESS
  • awardedFreelancerId set
BidRepository.rejectAllPendingBidsExcept()

Atomic MongoDB bulk-reject operation.

Rate Freelancer

  • Project must be COMPLETED
  • Calls FreelancerService.addRating()
  • ratingSum += score, totalRatings++
  • Average computed on demand
Complete / Cancel

Calls ClientService.incrementCompleted() or incrementCancelled() to update client reputation.

Docker & Semantic Versioning
Lab 6 · Deployment

Docker Strategy

  • Multi-stage Dockerfile (builder + runtime)
  • Image tagged with semver
  • Auto push to Docker Hub: ${DOCKER_HUB_USERNAME}/prod-eng-img:x.y.z
  • Deploy via Docker Compose profiles
  • Jenkins has Docker socket access (/var/run/docker.sock)

Docker Compose Profiles

prod-eng-service · monitoring · mongo · perf

Each profile starts an independent subset of services.

Semantic Versioning

ComponentHow it's derived
MAJORfrom last git tag (e.g. 1.23.0)
MINORauto-incremented on every build
PATCHfrom last git tag

Example: after a merge, if last version was 1.22.0, the new build produces tag 1.23.0 and image prod-eng-img:1.23.0

Alerting — Why? How does it work?
Lab 9 · Alerting

The Problem

  • Dashboards show WHAT happened — not THAT something happened
  • Someone has to watch them around the clock
  • 3 AM incident → nobody knows

The Solution

Prometheus evaluates rules → AlertManager sends email automatically → engineer responds. A fully closed loop.

Alert Lifecycle

StateWhat happensfor:
InactiveCondition is false, everything ok—
PendingCondition is true, waiting for durationrunning
FiringAlertManager receives it, sends emailelapsed
ResolvedCondition becomes false, resolution email sent—
The "for:" field

Debounce — avoids false alerts for momentary spikes. Container down → for: 0m. Latency → for: 2m.

AlertManager — Configuration
Lab 9 · AlertManager

Severity-Based Routing

SeverityReceiverRepeat
criticalcritical-email5 min
warningwarning-email30 min

Email

From: ingeni***@gmail.com
To: cla***@tra***.com
SMTP: smtp.gmail.com:587
Auth: Gmail App Password

Inhibition

If a CRITICAL alert is active, the WARNING for the same alert_group is automatically suppressed.

Example: ServiceHealthCheck CRITICAL active → ServiceHealthCheck WARNING is inhibited. One email instead of two.

Security

The real infrastructure/alertmanager/alertmanager.yml is gitignored because it contains SMTP credentials.

Grouping

ParameterValue
group_byalertname, severity
group_wait10s
group_interval10s

Alerts with the same alertname + severity are grouped into one email. Prevents spam during large incidents.
